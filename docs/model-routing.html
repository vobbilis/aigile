01 / The architectural question

Route the work.
Then route the request.

Task-weighted routing is not, by itself, an argument for harness placement. The placement argument is about who has the context, who can enforce the decision, and who can close the feedback loop.

A harness is the system that plans work, starts agents, controls tools, tracks task state, and checks results. A gateway is the shared service that admits and dispatches model requests. They make related but different decisions:

CAPABILITY

What kind of reasoning, tool use, and error tolerance does this task require?

ELIGIBILITY

Which model configurations satisfy that requirement and the organization’s policies?

DISPATCH

Which eligible endpoint is healthy, within budget, and available now?

The harness defines the task’s capability contract. The gateway enforces global policy and serves an eligible route. Both contribute evidence.

“Near the harness” means inside its task-and-outcome control loop, not necessarily inside its process. Classification can run in a shared service. Policy and model catalogs can be centrally managed. What should not disappear is the connection between the task definition, the route selected, and the result that proves—or disproves—the choice.

A gateway may see full prompts, tool messages, session metadata, and supplied task records. It is not inherently limited to “just tokens.” But request visibility alone does not guarantee access to the authoritative acceptance criteria, the actual child-agent path, or later validation results. A workflow-aware router can obtain those; the interface is the architectural issue.

A bounded claim

This case is strongest for multi-step engineering agents. It does not say every chat, embedding call, or fixed extraction task needs a planning panel and retrospective. Nor does it prove that a harness-side router is faster or cheaper: those are hypotheses to measure.

02 / Ten reasons, with the distinction intact

Four reasons for placement.
Six benefits of the policy.

The first four explain why the harness must participate. The remaining six explain why task-weighted selection is useful. Those benefits are not exclusive to a harness; a well-integrated central router can deliver them too.

The harness-placement case / 01–04
01

The task contract carries information the request may omit.

A short authorization edit can require more judgment than a long fixture update. The planner knows the design constraints, failure surface, dependencies, and whether a wrong result is cheaply detectable. Aigile classifies from those properties, not prompt length or file count alone.

Placement advantage Preserve the task’s meaning at its source. A gateway can classify well if it receives that contract; it should not have to reconstruct it from an isolated request.

02

Routing changes the team, not just the next completion.

The v4 planner classifies tasks before composing agents. It can resolve an open design question, separate mechanical edits from reasoning work, and keep each agent’s assignment model-homogeneous. Prompt rules state the contract; the Python Stop hook rejects missing routing and mixed-class agents; task ownership constrains execution. The hook checks structural consistency, not whether the chosen class is truly adequate.

Placement advantage A request router cannot split work it has not been given authority to plan. Gateway dispatch can still honor task/session affinity and negotiate an explicit change instead of silently switching a stateful agent’s model.

03

The actual agent path must be checked end to end.

In RL-001, the lead reached the intended proxy route while child agents ran stock Haiku. RL-002 also records that child working directories differed from the lead’s. A healthy gateway cannot establish a child’s environment or filesystem context. The harness owns spawning, can check the child’s actual route and directory, and can join that evidence to its assignment.

Placement advantage Combine both views. A gateway cannot account for a child that bypassed it without additional instrumentation. A transcript model field is useful runtime evidence, not cryptographic proof of the physical model behind a proxy. Read the evidence limit.

04

The outcome must reach the next plan.

HTTP success is not a correct implementation. The harness observes validation, repair attempts, scope deviations, and stalled tasks, then connects them to the original assignment. Its planner can use the result to change the next classification—or to write a more explicit task before choosing any model.

Placement advantage Keep task-level outcome ownership in the workflow. A central learner can consume those events and return recommendations; without that feedback, it is optimizing requests without knowing whether the work succeeded.

The task-weighted-routing case / 05–10
05

Spend against the risk of being wrong.

Use an adequate lower-cost class for specified, checkable work; reserve stronger reasoning for ambiguity, concurrency, security-sensitive design, or costly failure. The objective is total cost per accepted task, including validation and rework—not the cheapest token or the most prestigious model.

Compared with “Frontier everywhere” overbuys some work; “cheapest everywhere” can underbuy judgment. Net savings and faster completion remain unmeasured for this flow.

06

Grade the task, not the agent’s job title.

Two “test-writing” jobs may mean copying exact assertions or discovering adversarial cases. Two documentation jobs may mean transcribing evidence or resolving an architectural conflict. A task rubric recognizes the difference that a fixed builder/tester/writer-to-model table misses.

Compared with Role-based routing is simple, but role names are poor proxies for judgment. Aigile’s REASONING, STANDARD, and MECHANICAL classes describe the work, not the profession.

07

Cheap execution has to be earned by specification.

Aigile calls a task MECHANICAL only when the change is explicit, design freedom is absent, the tool sequence is bounded, and validation can catch a wrong result. If the planner cannot describe it that literally, it must clarify, split, or classify it higher.

Compared with “Looks easy” passes unresolved work downstream. This rule moves ambiguity resolution upstream and makes the lower-cost assignment a testable engineering claim.

08

Keep competence requirements separate from vendor names.

The spec names a class; a deployment binding selects a model/backend. That makes plans portable across approved cloud, local, or mixed configurations. But a label is not a universal capability guarantee: model version, reasoning settings, context limits, tool protocol, and harness behavior all affect suitability.

Compared with Hard-coded names entangle the engineering plan with deployment. The September 3 demo supplies actual mixed-model execution evidence. Abstract classes make that possible; they do not eliminate the ongoing cost of calibration or prove one backend’s superiority.

09

Make fallback an explicit policy, not a silent downgrade.

v4 promotes unavailable classes upward, honors task-specific caps, and stops if no acceptable route exists. Record the planned class, runtime-reported model, and fallback reason. In a gateway integration, organization-level policy and budgets must also constrain the eligible routes.

Compared with “Use whatever responds” can violate the task’s assumptions. Promote-only is an eligibility policy—not proof that a more expensive or higher-labelled model is stronger on every task.

10

Turn failures into conditional lessons, not model folklore.

A wrong implementation, an ambiguous spec, an unavailable endpoint, and a stalled validator are different failures. The retro records what happened and under which binding. A later planner can apply a matching lesson, challenge it, or decline it when the setup differs.

Compared with A flat pass/fail router can learn the wrong cause. Five ledger entries contain twelve scored verdicts across three repositories, plus a no-verdict, a lead-run validator note, and one correction. That is early operational evidence—not a learning curve—and the strongest mixed-model run is still absent from the ledger.

03 / The strongest opposing case

The gateway advocate
has a legitimate objective.

A gateway team is often optimizing a fleet: shared budgets, quotas, regional restrictions, approved providers, capacity, and service availability. A harness team is optimizing completion of a particular task. Neither objective is optional. They operate on different information and timescales.

“Central routing gives us one policy, not a hundred implementations.”

Agreed. Keep model catalogs, spending limits, access controls, and residency enforcement centrally governed. Harness-supplied class and rationale are inputs, not authority to bypass policy. A shared classifier can also prevent rubric drift across clients. The harness still needs to supply the task contract and react when no eligible route exists.

“Our router can read the prompt and infer difficulty.”

It can. For well-defined single requests, that may be sufficient. For an agent, the question is whether the prompt includes authoritative task scope, validation strength, unfinished dependencies, and the cost of a bad change. If the router receives those explicitly, the information gap narrows. Calling that service a gateway does not invalidate it.

“Global traffic gives the gateway better learning data.”

Potentially: more observations and broader capacity visibility are real advantages. But a large sample of successful HTTP responses is not a sample of successful tasks. Join serving telemetry to task outcomes, control for different models and harnesses, and feed the resulting policy back to planning. That is a shared task-aware control loop, which is compatible with this position.

“A model grading its own work is not a reliable router.”

Correct as a risk. The planner chooses the decomposition and class, so its blind spots can affect both. v4 already adds a separate routing challenger for medium/complex plans, unless the panel is disabled. That is an additional LLM critique, not independent ground truth. Simple plans normally skip it, and passing tests only prove the properties they actually cover.

“A new binding can invalidate your class labels.”

Yes. Calibration is an ongoing cost, not a one-time naming exercise. A result on stock Haiku does not establish what a shim-backed DeepSeek agent will do. Recheck the model version, tool protocol, context settings, and deployment path whenever they change. Use explicit capability requirements and applicable evidence, not a price tier masquerading as a guarantee.

“Your routing machinery may cost more than it saves.”

Also correct as a possibility. Classification, probe agents, critiques, duplicated context, retro, and repairs all consume time and tokens. Small tasks may be better served by a fixed approved model—or a deterministic script. The payoff is more plausible across heterogeneous, repeated builds, but it must be measured rather than assumed.

Where the disagreement resolves

A context-rich central router and a harness-integrated router can implement the same policy. The defensible objection is to routing detached from task context and outcome ownership, not to a network hop or central service.

04 / A practical division of responsibility

A capability contract,
not a turf boundary.

Recommended integration · not an implemented v4 API
Keep each decision with its authoritative inputs
DecisionHarness contributionGateway / platform contribution
What does the task need?Scope, design freedom, failure surface, validation contract, tool requirements.Publish calibrated capabilities and policy; optionally host the classifier.
What is allowed?Carry trusted task/data policy labels; request only within granted authority.Enforce identity, approved models, residency, quotas, and budgets independently of model judgment.
What serves the work?Request a compatible configuration and task/session affinity.Choose an eligible live route; return the resolved configuration and fallback reason.
What if the route changes?Checkpoint, approve the transition, or stop; account for state and tool side effects.Honor the contract or report that it cannot be met. Do not silently substitute an incompatible route.
Did it succeed?Attach acceptance evidence, failures, repairs, and task identity.Attach cost, latency, errors, model/backend identifiers, and request correlation.
What changes next time?Apply relevant lessons before classifying or decomposing new work.Aggregate eligible observations, recalibrate configurations, version shared policy.

A minimal exchange would carry a task_id, contract version, required capabilities, tool/context needs, and policy references; return a decision ID, resolved configuration, and fallback explanation; then accept a task-outcome event linked to that decision. Send the minimum necessary context—often structured metadata and evidence references, not the entire repository.

Hard constraints come from authorized policy, not an LLM’s suggestion. “Promote” must still mean eligible: a larger cloud model is not a permitted substitute for a local-only task, and price is not a compatibility test. No suitable route means stop or request an authorized policy decision.

Current flow versus proposed extension

Today’s v4 commands assign one model class per agent, resolve slots at deployment, verify runtime-reported bindings, and use bounded repair cycles. They do not implement this generic gateway contract, a fleet-wide optimizer, or automatic capability escalation after every quality failure. Mid-task reassignment would need an explicit checkpoint/restart policy.

Evidence first.
Claims at the right scale.

The v4 commands specify a routing rubric, a conditional plan-review panel, deployment checks, and a retrospective read/write path. The ledger has five entries from three repositories: twelve scored class verdicts, one “no verdict,” one lead-run validator note, and one correction. RL-001 is a deliberate calibration exercise; RL-003 rebuilds RL-002; RL-005 corrects RL-004 rather than recording a new build. These are not independent samples from a representative workload.

Open reliability question · September 3 versus September 4

The September 3 children reported the intended mixed-model routing. The September 4 RL-001 children reported stock Anthropic models instead. The records establish the difference, not its cause. The blanket statement “teammates never inherit routing” is too strong; “this launcher always propagates its bindings” is also unsupported.

Compare launch mode, spawn path, permissions/auth state, runtime versions, and child environment using controlled runs. Then test the actual child binding on every deployment. Until the difference is explained, mixed-backend routing is demonstrated in one configuration, not established as reliable across launch modes. This is a first-class open item, not a footnote.

The learning mechanism exists; its benefit remains to be established.

The planner is instructed to read binding-qualified lessons and cite applied entry IDs. The build writes rationale → observation → verdict → a conditional lesson. Call this an early feedback mechanism. To demonstrate better routing, show which subsequent classification changed, why the binding matched, and how the new outcome compared with the prior policy. This is policy adaptation through recorded context, not model-weight training.

The ledger gap is explicit: RL-001–RL-003 all concern Anthropic bindings, and this is still true with RL-004 and RL-005. The September 3 mixed-model demo predates the first entry and has not been absorbed into the planner’s ledger. This documentation update does not backfill or rewrite that history. A future append-only entry should distinguish its retrospective transcript check from the original environment-based report and carry narrow “apply when” conditions.

A current limitation worth fixing

The documented ledger-write path is in post-validation Wave 2. Exhausted failed builds skip that wave. A fair calibration record must retain failed, timed-out, and abandoned attempts too; otherwise the retro can learn mostly from survivors. Recording those outcomes independently of successful documentation is a recommended improvement, not a feature claimed here.

06 / How this argument can lose

Measure the completed task.
Include the routing tax.

A placement argument earns its keep by outperforming a credible alternative, not by weakening that alternative. Compare policies on a representative, held-out task set with the same model pool, tool permissions, starting state, and acceptance gates.

Four approaches to compare, not four predetermined winners
ApproachWhat it establishes
Fixed approved modelsRun lower-cost and stronger-model baselines. Simple workloads may not justify any dynamic routing.
Request-aware gatewayUse the prompt, normal request/session signals, policy, cost, and health. State exactly what information it receives.
Harness-integrated classifierUse the task contract, task graph, and binding-qualified outcomes to select and assess capability.
Shared task-aware routerGive a central service the same contract and outcome feedback. This isolates physical placement from the benefit of better information.
  • Quality: acceptance pass rate, task-specific negative tests, independent review findings, and escaped defects—not a model’s confidence or HTTP status.
  • Cost and time: all inference, classification, probes, critiques, retries, validation, retro, and human intervention. Include failed attempts; report cost per accepted task and median/tail completion time.
  • Fairness: repeat runs, control cache warmth and concurrency, version prompts/tools/bindings, and separate infrastructure faults from quality failures.
  • Learning: compare a frozen policy with a ledger-adjusted one on new tasks. Record the applied lesson and changed decision; do not treat one successful expensive run as proof that a cheaper model would have succeeded.
  • Scope: test tiny edits as well as multi-agent builds. Report routing overhead and the workloads where a fixed route wins.

For a placement-only comparison, freeze the task decomposition and rubric. If better planning is allowed to change the task graph, report that as an integrated workflow benefit rather than attributing every gain to where the router runs.

What would change our conclusion?

If a request-aware gateway meets the same quality gates with lower total cost and time on the target workload, use it. If a shared task-aware router matches or beats local classification, centralize the classifier. Neither result removes the need for task context, trustworthy route correlation, and outcome feedback; it changes how best to provide them.

Put routing judgment where the task contract and its outcome can meet. Keep infrastructure policy shared. Win on verified work—not on the location of the router.
