Introduction

Three Commands, One Pipeline

You describe what to build. The system grounds it in your design, plans it as a TDD-grade spec, red-teams the plan, builds it with a team of agents each running on the right model, and produces a mergeable PR — while you get coffee.

/plan_to_build_v4
↓
specs/*-v4.md
Reads your ADRs and design docs, writes one spec with types, named tests, a task graph and a model-routing plan, then has four critics attack it before it is blessed
/build_v4
↓
working code + Build Evidence
Deploys a self-organizing team, each agent on the model slot its work needs, validates against the spec, writes evidence and a routing lesson back into it
/bug_to_pr
↓
merged PR
Triages the bug, routes to specialist, fixes with full pipeline, adversarial review, merge gate
For the unfamiliar
Think of this as a self-managing engineering team. You play the role of product owner — you describe what needs to happen and make final decisions. The system handles investigation, planning, coding, testing, reviewing, and creating the PR. In v4 it also decides which team member needs a frontier model and which can run on a cheap local one, and it learns from each build whether it guessed right. Each command produces a real artifact you can inspect and modify.
For the architect
The spec file is the coordination artifact and the system of record, and alignment to it is continuous: every hop from design to spec to code to evidence is gated, and the loop closes back into the design doc before the next increment starts (see Why It Works This Way). On Claude Code the team runs on native primitives — a shared task list with dependencies, agents deployed once with standing orders, peer messaging, and a lead that never writes code. Every task carries a Model Class (REASONING / STANDARD / MECHANICAL) derived from its shape; agents are partitioned so each is single-class and deploys on the matching slot, which the session's launcher binds to Bedrock or a local model. Enforcement sits at three levels: prompt rules, Python hooks on tool events and session stop, and structure (disallowed tools, read-only critics, transcript-verified bindings). The Copilot variant compensates for missing task primitives with the spec file alone.
Also runs on Codex
The v4 commands are ported to Codex as native skills, $plan-to-build-v4 and $build-v4, with seven registered roles (builder, validator, reviewer, spec-updater, design-updater, auditor, plan-critic). Stock Codex coordinates the agents; there is no controller to run. A recorded smoke build on Codex 0.144.1 ran the full sequence — builder, validator, two independent reviews, both updaters, a fresh auditor — and repaired an injected fault. One known limit: child agents inherit the parent's permission profile, so read-only roles are instruction-only. There is no tarball for this side; the skills are three directories copied from codex-v4/native. Guide and evidence: NATIVE_WORKFLOW.md.

Command 01

Plan to Build v4

/plan_to_build_v4

Turns a design-grounded requirement into one TDD-grade spec — types, named tests, task graph and model routing — that a team of agents can execute without asking questions, and that four critics have already tried to break.

The most important insight in this system: the spec is the contract. Everything downstream — builders, validators, the lead, the spec-updater — works from the spec and nothing else. Since v3 the spec is a single file that holds both the design thinking and the build orchestration, because they describe the same work. Since v4 it also predicts which class of model each agent needs, and that prediction is scored after the build.

"The intelligence is in the spec. The build lead is a router, not a coder." Design principle

What It Does

  • A
    Grounding Analysis

    Reads every ADR and design document the prompt points to, extracts the locked decisions (D-NNN), and verifies every file:line reference directly — no subagents, because pins relayed through a summary are how fictional references enter specs. Reads the routing ledger and applies prior lessons whose conditions match this work.

  • B
    Conditional Design Study

    Skipped when the prompt is fully grounded. Otherwise runs the full study — domain enumeration, security, correctness, performance, scalability, industry comparison, 10x opportunities — and writes docs/design/<domain>.md first. The spec derives from the design, never the reverse.

  • C
    Author the Spec in Stages

    Skeleton first, then one edit per section so progress is visible and recoverable. Type Surface with a Failure Surface block per non-trivial type, authored before tests. Test Promises: every test named and categorised, each failure-mode bullet mapped to a row, at least 30% failure-path. Then the task graph — each task with Assigned To, Depends On, Model Class, and an exhaustive description that points back at the types and tests it builds.

  • C
    Classify, then Partition

    Every task is classified REASONING, STANDARD or MECHANICAL by its shape. Agents are composed so each holds a single class — split or promote, never mix. The Model Routing section records each agent's class with a rationale concrete enough to score later, plus a promote-only fallback policy.

  • C.5
    Red-Team the Draft

    For medium and complex specs, four read-only critics run in parallel: a failure-surface adversary, a grounding auditor, an omissions critic and a routing challenger. They return numbered findings with fixes. The author adjudicates each one — accept and edit, or reject with a stated reason — and records the panel in the spec. One author, many critics, nobody co-authors.

  • ✓
    Stop Hooks Gate the Session

    The session cannot end until a new specs/*-v4.md exists and passes validate_v4_spec.py: all required sections, a typed Type Surface, named test rows, complete task fields, failure-surface coverage, and one Model Class per agent. The spec carries an EXECUTION DIRECTIVE forbidding direct implementation.

Spec Quality Rules

These rules are embedded directly in the command and checked by hooks — not left to a skill file that might not load.

Rule What it prevents Enforced by
Every claim traces to a D-NNN or design section Hallucinated APIs and architectural choices nobody decided prompt author verifies pins · structural grounding auditor re-checks
Failure Surface before Test Promises Happy-path-only specs system hook blocks if error/config/stateful types lack matching test categories
Tests are named, not described Validators that cannot tell PASS from FAIL system hook requires test rows; ≥30% failure-path or warning
Exhaustive task descriptions with type + test references Builders improvising signatures or asking questions they cannot ask system hook checks required task fields
Assigned To + Model Class on every task Wrong builder on a task; expensive model on transcription work system hook blocks missing fields and mixed-class agents
Scoreable routing rationale "Seems simple" classifications that cannot be learned from structural routing challenger critic · post-build retro
Stable content first, volatile last Prefix-cache misses when N builders re-read the spec prompt section ordering rule
Staged writes, never one giant Write A 20-minute stream that looks like a hang and loses everything on interrupt prompt skeleton + one Edit per section
EXECUTION DIRECTIVE Main agent implementing code directly instead of delegating prompt embedded in every spec
Command 02

Build v4

/build_v4

A team lead, not a coder. Resolves the routing plan against the models actually reachable, deploys a self-organizing team once, monitors by message, and writes evidence and a routing lesson back into the spec.

The lead makes no design decisions. It reads what the spec says, turns the task graph into a shared task list with dependencies, and deploys each agent with standing orders and an explicit model slot. From there the agents self-organize: builders claim only tasks addressed to them, the validator creates fix tasks, and the lead intervenes only for hung agents or exhausted fix cycles. Its own tools for writing files are disabled.

Model Routing at Deploy Time

The spec names a class per agent. The lead maps class to slot, discovers what the session's launcher bound each slot to, probes each slot with a one-shot teammate and reads the physical model from its transcript — teammates do not inherit the launcher's environment, so env vars are advisory only. Dead slots promote agents one class up, never down. The resolved table is announced before anything is deployed.

REASONING
slot: opus · e.g. Bedrock Fable
Failure-surface-dense types, concurrency, crypto, cross-module refactors, any task that leaves design judgment to the agent.
STANDARD
slot: sonnet · e.g. GLM on the lab box
The default. Test construction from named promises, the validator's command execution and pass/fail adjudication.
MECHANICAL
slot: haiku · e.g. DeepSeek via shim
Byte-specified diffs with zero design freedom and a validation command that catches a wrong result. Spec-updater and design-updater live here.

The Rules the Lead Never Breaks

Rule Why it exists
NEVER write code yourself Write, Edit and NotebookEdit are disabled on the lead. Every change goes through a deployed agent.
Deploy agents ONCE with standing orders Agents self-organize around the task list. Re-deploying per task recreates the micromanaging orchestrator v1 replaced.
Pass model: slot on every deployment Omit it and the agent silently inherits the session model. The routing plan becomes fiction.
Verify the binding from transcripts The first ledger entry exists because announced routing did not match what teammates actually ran on. Env vars describe the lead's session, not the teammates'.
Promote, never demote A dead cheap slot must never downgrade REASONING work. If the REASONING slot is dead, stop.
Do NOT poll — wait for messages Tight TaskList loops burn the lead's context. Completion reports arrive via SendMessage.
Max 2 fix cycles, then escalate Prevents infinite loops. After two failures the validator escalates and no Wave 2 runs — there is no evidence to write.
Wave 2 only on validate-all PASS Spec-updater and design-updater have nothing to do until validation passes. Deploying early burns tokens on idle heartbeats.
Reset at ~75% context, never /compact At the wall /compact 400s and the lead wedges while builders keep working blind. /clear is client-side and preserves the team; re-anchor from git and the task list.

The Builder's Contract

Every builder is deployed with the same standing orders, identity-last so the shared prefix is cached across builders. The shape of the work is not in the prompt — it is in the spec:

Standing orders — shared body, per-agent identity at the end
1. Read the spec. ## Type Surface and ## Test Promises are the authoritative shape contract — never improvise a signature or a test name.
2. Claim only tasks whose description contains Assigned To: <your name>. Skip everything else, even if unblocked.
3. Execute, mark completed, report to the lead, go back to the task list. Poll every 10 seconds; heartbeat every third idle cycle.
4. If the task and the spec conflict, the spec wins — surface the conflict in your report.
5. Never self-terminate. A shutdown_request from the lead is the only exit; echo its request_id and stop immediately.
Command 03

Bug to PR

/bug_to_pr

A complete local async pipeline. Describe a bug; receive a reviewed, adversarially-approved, mergeable GitHub PR — with full audit trail attached.

This command deliberately beats the GitHub async Copilot workflow by running everything locally with your full hooks, TDD enforcement, and nested orchestration — but still produces a proper GitHub PR with attached artifacts. You walk away. The pipeline works. You come back to a decision: merge or reject.

The Six Phases

  • P0
    Setup

    Generates BUG-NNN ID, creates bugs/BUG-NNN/ directory, creates fix/bug-nnn git branch, initialises pipeline state file for crash recovery.

  • P1
    Triage

    bug-creator investigates the codebase, reproduces the bug, writes a JIRA-format report with all 8 required sections (hook-enforced). bug-router reads the report and module registry, routes to the correct specialist fixer.

  • P2
    Fix (nested orchestration)

    Phase 2a: specialist fixer reads bug report and creates a fix spec (the plan_to_build equivalent). Phase 2b: orchestrator runs the full build protocol inline — TDD, validators, fix cycles, rollback. Phase 2c: captures test evidence to bugs/BUG-NNN/test-results.md.

  • P3
    PR Creation

    Commits and pushes the fix branch. Opens PR with structured body. Posts the full bug report as a PR comment — the PR becomes the audit hub.

  • P4
    Adversarial Review

    reviewer-alpha runs independently, verdict held in memory. reviewer-beta runs independently — alpha's file does not exist yet (structural isolation). Only after both complete are review files written to disk and posted as formal PR reviews.

  • P5
    Merge Gate

    Both reviewers must APPROVE. You confirm. Pipeline merges and deletes the branch. If either rejects, presents reasons and offers a retry fix cycle (max 2 total).

Adversarial Review Isolation

Reviewer isolation is enforced structurally rather than by a hook. The orchestrator holds both verdicts in memory and writes nothing to disk until both reviewers have completed:

Isolation protocol
Step 1: Dispatch reviewer-alpha. Verdict returned in response text. Do NOT write to disk.

Step 2: Dispatch reviewer-beta. bugs/BUG-NNN/reviews/alpha.md does not exist yet — it cannot be read even if beta tries.

Step 3: Only after both verdicts are held in orchestrator memory: write both files simultaneously, then post as gh pr review.

What's genuinely lost: No system-level enforcement prevents the orchestrator from accidentally writing alpha's file before dispatching beta. This is protocol discipline, not hardware guarantee.

Crash Recovery

Sessions can crash. Pipeline state is written to disk after every phase. On restart, the orchestrator reads bugs/BUG-NNN/pipeline-state.json and resumes from exactly the right phase — no re-running completed work.

Design Philosophy

Why It Works This Way

The Spec Is the Contract

The build lead makes no design decisions — it reads what the spec says and routes it. All intelligence is front-loaded into the spec by /plan_to_build_v4. This constraint is intentional: a lead that only coordinates is predictable, auditable, and trustworthy in a way that a decision-making orchestrator is not.

The spec must be airtight because the lead is mechanical. This is not a limitation — it is a design choice that produces better specs. When the executor cannot compensate for vagueness, the planner has no choice but to be precise. v3 made that precision typed and test-shaped; v4 made the planner's blind spots someone else's job to find.

"The spec is the contract. Everything downstream — builders, validators, reviewers — works from the spec and nothing else." Design principle

The Alignment Loop

Incremental development is where AI-written code usually rots. The second increment gets planned against a design doc that describes the first increment's intentions, not its code, and the gap compounds from there. The v4 flow treats alignment as work, not as an assumption: every hop from design to spec to code to evidence has a gate that checks the artifact against the one behind it, and the last agent to run rewrites the design doc from the actual diff. The next increment grounds on what was built, not on what was meant.

None of this depends on anyone remembering to check. The gates are held by different parties — the author, four critics, a hook, a read-only validator, two post-build agents — and the two that matter most run after the code exists. The build report closes with the same reconciliation: types built versus promised, tests passing versus promised, deviations listed by name.

Classification Is a Prediction, Not a Preference

Routing a task to a cheap model is a falsifiable claim: "this work needs no design judgment and a listed command will catch a wrong result." The build tests that claim. The lead watches for capability signals — fix cycles, stalls, off-spec output, or a cheap slot breezing through — and scores each agent RIGHT, OVER-PROVISIONED or UNDER-PROVISIONED. The lesson lands in the spec and in an append-only ledger, keyed to the physical models that were actually running, and the next planner reads it before classifying anything. Each build pays for the next one's accuracy.

Skills vs Embedded Philosophy

The system ships a library of skills covering planning, TDD, systematic debugging, verification before completion, safe rollback, and more. Skills are loaded on relevance — the model decides whether to pull them. That's probabilistic. Under pressure, the model might not load the right skill.

The solution: embed the critical rules directly in the commands and agent standing orders where the model cannot choose not to read them, and back the ones that matter most with hooks. Skills are the source of truth. Prompts and hooks are the enforcement layer.

Local vs Async — The Comparison

The local pipeline is not a compromise version of async — it is the superior workflow for work that demands quality. You can launch multiple /bug_to_pr sessions simultaneously, one per terminal, each on its own branch, each running the full pipeline autonomously. Go to lunch. Come back to multiple PRs — each with a JIRA bug report, test evidence, and two independent adversarial review verdicts attached. That is genuinely parallel async work, locally, with no quality compromised.

The GitHub async Copilot workflow produces a PR. The local pipeline produces a PR plus everything the async workflow cannot: mandatory TDD on every task, hooks that block bad code at write time, adversarial review by two isolated agents, semantic merge conflict resolution, and a full audit trail from triage through merge gate. The only thing the async workflow adds is that no terminal needs to be running — a marginal advantage when your terminal is already open.

Use the local pipeline for work you care about. Use the async GitHub Copilot workflow only for pure delegation — simple, low-risk tasks you would assign to a junior developer and review later, where quality gates can be lighter. For everything else, the local pipeline wins.

One more advantage worth stating plainly: the local pipeline is completely portable. It runs in any IDE, against any git-compatible repository — GitHub, GitLab, Bitbucket, self-hosted Gitea, whatever your organisation uses. The GitHub async Copilot workflow is locked to GitHub.com. If your team is on GitLab or your enterprise runs an internal git server, the async workflow is simply unavailable. The local pipeline has no such dependency.
