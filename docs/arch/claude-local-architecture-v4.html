Evolution — v1 → v2 → v3 → v4, and the problem each one fixed
v1
March 2026 · /plan_to_build → /build
Self-organizing agent teams
  • Planner writes an exhaustive spec to specs/; Stop hook validates 7 required sections
  • Leader creates a team, one TaskCreate per task with addBlockedBy deps, deploys builders + validator + spec-updater once with standing orders
  • Agents poll TaskList, claim by role: prefix, execute, report via SendMessage
  • Validator creates fix tasks, max 2 cycles; spec-updater writes Build Evidence back into the spec
what broke any builder could claim any builder task; builders self-terminated after 5 idle polls and orphaned fix tasks; team names collided on re-run; hung agents were invisible
v2
March 2026 · /plan_to_build_v2 → /build_v2
Reliability + design-first planning
  • Assigned To enforced — builders only claim tasks addressed to their own name
  • Indefinite polling — shutdown_request is the only exit; validator names the builder and the leader sends a targeted wakeup
  • Timestamped team names; leader tracks last_seen, pings at 10 min, escalates at 12
  • Planner runs a full design study and writes docs/design/<domain>.md first; plan tasks derive from it; a design-updater agent writes back what was built
  • Three-layer shutdown: polite request → TeamDelete retry → tmux pane kill
what broke design thinking and build orchestration lived in two files (a TDD plan and a v2 spec) that drifted; specs were happy-path-only; tests were described in prose, not named
v3
Mid 2026 · /plan_to_build_v3 → /build_v3
Unified TDD-grade spec
  • One file: Design Grounding, Type Surface, Test Promises, RED-GREEN-REFACTOR and the task graph in a single -v3.md
  • Failure Surface blocks per type, authored before tests; every bullet maps to a named test row; ≥30% failure-path tests or the hook warns/blocks
  • Every spec claim traces to an ADR decision (D-NNN) or design-doc section; file:line pins verified by the author, no subagents
  • Two-wave deploy: spec-updater and design-updater deploy only after validate-all passes — no idle heartbeats during the build
  • Leader context resilience: reset via /clear at ~75% context and re-anchor from git + TaskList, never /compact
  • Staged spec writing (skeleton, then one Edit per section) so a 50–90 KB spec can never look like a hang
what broke every agent ran on the session model regardless of task difficulty — transcription tasks paid frontier prices, and the planner's own blind spots went unchallenged

September 2026 · /plan_to_build_v4 → /build_v4

v4 core — dynamic model routing

Classify by task shape · partition agents · bind at deploy

classes are abstract · bindings are the launcher's

The spec never names a physical model or backend. It names the class of competence each agent's task set requires. The fixed class→slot mapping is REASONING→opus, STANDARD→sonnet, MECHANICAL→haiku. What a slot resolves to is decided by the session's launcher: under claude-multi the opus slot is Bedrock Fable, the sonnet slot is GLM on the SGLang lab box, and the haiku slot is DeepSeek behind a LiteLLM shim; under claude-bedrock all three are Anthropic models and the classes express cost tiering only. The same spec runs either way without edits.

REASONING
slot: opus · any ONE trigger promotes the task
  • builds a type whose Failure Surface has ≥4 bullets
  • concurrency (Corner/Loom), adversarial or cryptographic work
  • cross-module refactor touching ≥3 files under back-compat
  • the description leaves ANY design judgment to the agent
  • public API surface design
STANDARD
slot: sonnet · the default
  • everything that is neither clearly REASONING nor fully MECHANICAL
  • test construction from named promises (promote when the tests are adversarial/Loom/property)
  • the validator: command execution + pass/fail adjudication
  • the routing challenger critic at plan time
MECHANICAL
slot: haiku · ALL triggers must hold
  • the diff is fully specified: exact files, exact content shape
  • zero design freedom — transcribe, scaffold, repeat a pattern
  • linear tool sequence, roughly ≤10 calls, no subagents
  • a listed validation command catches a wrong result cheaply
  • spec-updater, design-updater, grounding-auditor critic

Partitioning rule. An agent is one process with one model for its lifetime, so routing happens at team composition. If a natural builder would hold mixed-class tasks, split it into two builders or promote the whole set to the highest class present. Promote, never demote. The v4 Stop-hook validator hard-blocks mixed-class agents.

Fallback policy. If a slot is dead at deploy time its agents move one class up (MECHANICAL→STANDARD→REASONING), re-checking liveness at each step. A dead cheap slot must never silently downgrade REASONING work. If the REASONING slot itself is dead, the build stops. Specs may cap individual agents ("builder-2 may not be promoted past STANDARD — 40-file fan-out is cost-prohibitive on the REASONING slot").

MECHANICAL caution. The haiku slot may be a non-Anthropic model behind an API-translation shim, measurably weaker at long agentic tool chains. Write MECHANICAL descriptions for the weakest binding the spec might deploy on: exact paths, exact content, one validation command. If it cannot be written that literally, it is not MECHANICAL.

v4 core — plan-time red team (Phase C.5)

One author, four critics — the draft is attacked before it is blessed

medium/complex only · read-only critics · model-routed

The planner still verifies every file:line pin itself. The critics never co-author: they return numbered findings as [PREFIX-N] BLOCKER|MAJOR|MINOR — section — evidence — fix, and the author adjudicates each one. A BLOCKER may only be rejected with a reason naming the evidence the critic missed. Simple specs skip the panel unless the prompt says panel: on. Every adjudication lands in the spec's ## Plan Review Panel, so the build retro can later score the panel too: a defect the build finds that a critic flagged and the author rejected is a ledger lesson.

CriticSlotClassCharter
FSA · Failure-Surface AdversaryopusREASONINGFor every error / config / stateful / builder / crypto type: is the Failure Surface complete, and does every non-trivial bullet have a Test Promises row? Names missing bullets and the tests they imply. Flags happy-path-only areas.
GRD · Grounding AuditorhaikuMECHANICALMechanically verifies every file:line pin at the stated Code Baseline with grep/sed, every cited D-NNN exists in the named ADR or design doc, every cited RL-NNN exists in the ledger with a matching "apply when:". One PASS/FAIL line per pin.
OMS · Omissions & Scope CriticopusREASONINGWhat does the grounding require that the spec neither builds nor explicitly defers? Deferred-without-saying items, scope claims with no acceptance criterion, "does NOT build" entries that contradict the task list.
RTG · Routing ChallengersonnetSTANDARDAttacks ## Model Routing. Every MECHANICAL task: byte-specified, zero design judgment, ~≤10 tool calls, or names the hidden judgment. Every REASONING task: not over-classified. Checks per-agent homogeneity, scoreable rationales, sensible fallback caps.

Artifact — what a v4 spec contains, and who reads each section

specs/<milestone>-v4.md — stable content first, volatile last

prefix-cache friendly · one file since v3

N builders read the spec concurrently and re-read it across polls. Backends cache on the longest common token prefix from position 0, so the immutable header and the shared design sections sit at the top and byte-stable for the whole build. The only top-of-file mutation is the Status line flipping DRAFT→COMPLETE once, after every builder has finished reading. Build Evidence is last by design.

v4 core — the routing ledger learning loop

Classification is a falsifiable prediction, not a preference

read at plan time · written at Wave 2 · append-only

Each agent's rationale in ## Model Routing must be concrete enough to score after the build. "MECHANICAL because the diff is byte-specified and one clippy run catches errors" is scoreable; "seems simple" is not. During the build the lead logs routing signals: fix cycles (capability or spec ambiguity?), stalls, off-spec output, cheap-slot agents that breeze through, promotions. At the Wave 2 trigger the lead composes the retro, and the spec-updater transcribes it verbatim into Build Evidence and appends a ledger entry.

Lessons are keyed to their binding: line. A verdict earned where the haiku slot was claude-haiku-4-5 says nothing about a shim-backed DeepSeek slot. The first ledger entry exists because the announced binding turned out to be fiction: teammates do not inherit the launcher's environment, so the lead's curl probes reached DeepSeek while the teammates ran on stock Haiku. That is why v4 reads the physical model from teammate transcripts and never from env vars.
